# Typed translations (LambderI18n)

Standalone, framework-free, isomorphic translation module. Zero dependencies, no Node or DOM requirements (browser detection is feature-gated), so it is safe to import in lambda backends and frontend bundles alike.

```typescript
import { createLambderI18n } from "lambder/client";
```

Browser code imports it from `lambder/client`, whose graph is browser-safe;
server code may import the same exports from `lambder`.

## Concepts

- **Language registry**: every language the app can serve, with metadata (`name`, `englishName`, `intlLocale`, `dir`, plus any app extras). Declared once at init.
- **Enforced languages**: the subset every dictionary must always provide (typically `["en"]`). The `defaultLanguage` must be one of them.
- **Base dictionary**: app-wide general keys. Strict: every language must provide every key.
- **Extensions**: components add their own keys on top of the base, either strictly (`extend`: all languages required) or partially (`extendPartial`: only the enforced languages required, everything else optional and falling back).
- **Loaders**: any language block except the default one can be a function that fetches the dictionary (`tr: () => import("./tr")`) instead of the dictionary itself, so a bundler splits each language into its own file and a visitor downloads only theirs.
- **Typed contract**: keys and `{token}` params are inferred from the `defaultLanguage` block at compile time. `t("greet")` is a compile error if `greet` is `"Hello {name}"`; `t("greet", { name: "Ada" })` is required.
- **Plural entries**: a text that varies with a count is an entry of forms keyed by plural category (`{ one: "{count} item", other: "{count} items" }`), and `t("items", { count })` picks the form under the plural rules of the text's language (see [Plural forms](#plural-forms)).
- **Placeholders kept**: every translation carries exactly the `{tokens}` of the default language's text it translates, in any order. One that drops a token would lose the value a caller passes, and one that adds a token would show it as it is, so both are refused where the translation arrives (see [Placeholders](#placeholders)).

## Setup

```typescript
// common/i18n.ts
export const i18n = createLambderI18n({
    languages: {
        en: { name: "English", englishName: "English", intlLocale: "en", dir: "ltr" },
        tr: { name: "Türkçe",  englishName: "Turkish", intlLocale: "tr", dir: "ltr" },
        ar: { name: "العربية", englishName: "Arabic",  intlLocale: "ar", dir: "rtl" },
    },
    defaultLanguage: "en",
    enforced: ["en"],
    base: {
        // The defaultLanguage block is the typed contract (keys + {token} params):
        en: { save: "Save", greet: "Hello {name}" },
        // base is strict, every language must provide every key:
        tr: { save: "Kaydet", greet: "Merhaba {name}" },
        ar: { save: "حفظ", greet: "مرحبا {name}" },
    },
    // Optional detector, tried before browser detection. What it returns is
    // matched case-insensitively; anything that is no code passes:
    detectLanguage: () => window.location.pathname.split("/")[1],
});
```

## Translating

```typescript
i18n.t("save");                    // active language, resolved automatically
i18n.t("greet", { name: "Ada" });  // params compile-time enforced from {tokens}

const t = i18n.forLanguage("tr");  // explicitly bound (per-request backend use)
t("save");                          // "Kaydet"
```

### Language resolution (auto `t`)

Evaluated on every read, nothing remembered, so a detector that reads the
path follows an SPA from `/en/` to `/tr/`:

1. `setLanguage(code)` override (user preference, switcher)
2. `detectLanguage()` from setup, if provided and it returns a supported code
3. Browser detection: ordered `navigator.languages`, matching the full code (`pt-BR` from `pt-br`) then the primary subtag (`de` from `de-AT`); skipped where there is no `document` (a server, a worker), because Node 21 and later, Deno and Bun fill `navigator.languages` from the process locale, and a server's locale is not its reader's
4. `defaultLanguage`

Language tags are case-insensitive (BCP 47), so every code that arrives at
runtime is matched that way and answered as registered: a browser's `pt-br`, a
detector's `PT-BR` and `setLanguage("pt-br")` all select a registered
`pt-BR`, and `currentLanguage` reads `pt-BR`. The same holds for
`forLanguage`, `loadLanguage` and `registerDictionary`. `isLanguageCode` is the
one exception: it narrows the string it is handed to a registered code, so it
answers true only for the spelling as registered. Two registered codes that
differ only in case are one tag twice, and `createLambderI18n` refuses them.
The config's own keys (`base`, an extension's blocks) use the registered
spelling, as their types already require.

Missing translations fall back per key: active language → `defaultLanguage` → the key itself. `t` never throws.

A language that detection picks up on its own is not announced to
`onLanguageChange` listeners and does not start that language's loaders: a
lazily loaded language falls back to `defaultLanguage` until `loadLanguage()`
runs (call it where the app changes what the detector reads, a route change
for instance).

Parameters are filled in one pass over the text: a value is inserted as it is,
so a display name `Eve {store}` passed as `{name}` stays `Eve {store}` rather than
having its `{store}` filled too.

### Placeholders

The compiler checks the params a call passes against the default language's
text; the other languages' texts are strings it cannot read. So each
translation's `{tokens}` are checked against the default language's text of
the same key when the translation arrives, and a block holding one that drops
or adds a token is refused, every such key listed in one error:

- an inline block, when `createLambderI18n`, `extend` or `extendPartial` runs,
  which is on the first load of every page and every test that imports it;
- a loaded block, when its loader answers: `loadLanguage` rejects and the
  language stays on the default one, as for a loader that failed;
- `registerDictionary`, which throws and registers nothing.

A language loaded on demand is checked only once something loads it, so a
test that loads every language checks them all:

```typescript
await Promise.all(i18n.languageList.map((code) => i18n.loadLanguage(code)));
```

A plural entry's forms are held to the same rule, with one allowance for
`{count}`; see [Plural forms](#plural-forms).

## Plural forms

A text that varies with a count is a plural entry: one form per plural
category, keyed by the category `Intl.PluralRules` sorts a count into
(`zero`, `one`, `two`, `few`, `many`, `other`). `other` is required: every
language uses it, and it is the form shown for a count whose category the
entry lacks. `t(key, { count })` picks the form for the count under the plural
rules of the language the text is in, read from that language's Intl locale
(`intlLocale`, or the code). English uses `one` and `other`; Arabic uses all
six:

```typescript
export const i18n = createLambderI18n({
    languages: {
        en: { name: "English", intlLocale: "en" },
        ar: { name: "العربية", intlLocale: "ar", dir: "rtl" },
    },
    defaultLanguage: "en",
    enforced: ["en"],
    base: {
        en: {
            items: { one: "{count} item", other: "{count} items" },
            ordersAt: { one: "One order at {store}", other: "{count} orders at {store}" },
        },
        ar: {
            items: {
                zero: "لا توجد منتجات",       // 0
                one: "منتج واحد",             // 1, in words
                two: "منتجان",                // 2, in words
                few: "{count} منتجات",        // n % 100 is 3 to 10: 3, 10, 103
                many: "{count} منتجًا",       // n % 100 is 11 to 99: 11, 99, 111
                other: "{count} منتج",        // the rest: 100, 101, 102, 200
            },
            ordersAt: {
                zero: "لا توجد طلبات في {store}",
                one: "طلب واحد في {store}",
                two: "طلبان في {store}",
                few: "{count} طلبات في {store}",
                many: "{count} طلبًا في {store}",
                other: "{count} طلب في {store}",
            },
        },
    },
});

const en = i18n.forLanguage("en");
en("items", { count: 1 });                           // "1 item"
en("items", { count: 5 });                           // "5 items"
en("ordersAt", { count: 1, store: "Main St" });      // "One order at Main St"

const ar = i18n.forLanguage("ar");
ar("items", { count: 2 });                           // "منتجان"
ar("items", { count: 3 });                           // "3 منتجات"
ar("ordersAt", { count: 11, store: "Main St" });     // "11 طلبًا في Main St"
```

- **Typed**: a plural key always takes params, a numeric `count` beside the
  tokens across its forms. `t("items")`, `t("items", { count: "2" })` and
  `t("ordersAt", { count: 2 })` (no `store`) are compile errors.
- **Every category the language uses**: an entry should hold a form for every
  category `new Intl.PluralRules(locale).resolvedOptions().pluralCategories`
  lists for its language's Intl locale. At runtime a missing one never fails:
  `t` shows the entry's `other` form for a count in that category, and logs
  nothing. `i18n.checkPluralCoverage()` is the strict check, for a test or a
  build (see [Checking plural coverage](#checking-plural-coverage)). A form for
  a category the language does not use is never picked and is never reported.
- **Refused where the dictionary arrives**: what every runtime judges alike is
  refused in the places [placeholders](#placeholders) are checked (creation,
  `extend`, `extendPartial`, a loader's answer, `registerDictionary`): a key
  that is no plural category, a form that is no text, an entry without
  `other`, a value that is neither a text nor a plural entry, and an Intl
  locale that is no well-formed language tag, for a language with plural
  entries (a language without them is never given to `Intl.PluralRules`).
- **Placeholders across forms**: every form, in every language, carries each
  token of the default language's forms, except `{count}`, which a form may
  leave out to name the number in words, as the Arabic `one` and `two` do.
- **Texts and plural entries for one key**: the default language's entry
  decides. A key whose default entry is a text is a text in every language: a
  plural entry for it is a compile error, and is refused at runtime, because
  `t` takes no count for that key. A key whose default entry is plural takes a
  plural entry in every language, or a plain text, which is taken as the
  `other` form alone: complete for a language whose rules use only `other`
  (Japanese, Chinese, Korean), and anywhere else a gap the check reports.
- **Fallback**: a language without the key falls back to the default
  language's entry, and the form is picked under the default language's rules,
  since the text is in that language.
- **The count as shown**: `{count}` is inserted as `String(count)`. To show it
  formatted (digit grouping, the language's own digits), use another token in
  the forms and pass both: `t("items", { count, countText: format(count) })`.

### Checking plural coverage

Which categories a language uses is plural data the JavaScript runtime ships
(CLDR, through `Intl`), and runtimes ship different versions of it. Newer
ones occasionally list one more category for a language: `many` for French,
Spanish, Italian and Portuguese, for counts such as a million, which older
browsers do not list. A dictionary written and tested on one runtime can
therefore lack a category on a visitor's newer browser. That must not stop the
page, so at runtime the count gets the `other` form. Gaps are found in a test
instead, on the runtime the test runs on:

```typescript
// i18n.test.ts
import { it } from "vitest";
import { i18n } from "./i18n";
import { checkoutI18n } from "./checkout/i18n";   // an extension

it("every plural entry has a form for each category its language uses", async () => {
    await i18n.checkPluralCoverage();
    await checkoutI18n.checkPluralCoverage();
});
```

`checkPluralCoverage()` first loads every language, as `loadLanguage` does for
each, so the languages behind loaders are checked too, and a loader that fails
rejects it. Then it checks every entry the instance translates with, its own
and its parents', by the entry `t` would use in each language, the default
language's included. It resolves when nothing is missing and otherwise rejects
with every gap, one line each:

```text
LambderI18n: these plural entries lack forms for categories their language's plural rules use, by this runtime's Intl plural data; t shows their other form for those counts:
  "items" in "ar" lacks few, many: "ar" uses zero, one, two, few, many, other
  "items" in "tr" is a text, which stands for the other form alone, and lacks one: "tr" uses one, other
```

An extension sees its parents but not its siblings, so check each leaf
extension. Run the test on the newest runtime you support: a form an older
runtime does not use is harmless, so the newest runtime's data is the one to
write every category for.

## Extending in components

```typescript
// componentA.ts, strict: every language must provide every new key
const cI18n = i18n.extend({
    en: { compute: "Compute" },
    tr: { compute: "Hesapla" },
    ar: { compute: "احسب" },
});

// componentB.ts, partial: only the enforced languages are required
const bI18n = i18n.extendPartial({
    en: { upload: "Upload" },      // required (enforced)
    tr: { upload: "Yükle" },       // optional, ar falls back to en
});

bI18n.t("upload");   // extended key
bI18n.t("save");     // base keys remain visible, key space is merged
```

- Extensions return a **new instance**; the parent is untouched. Extensions chain (`extend` on an extended instance).
- Extension keys must be **new**: redeclaring a key that already exists in the parent chain is a compile-time and runtime error (override translations at runtime with `registerDictionary` instead).
- All instances derived from the same root **share the active-language state**: `setLanguage` anywhere affects every translator instantly.
- Missing language blocks throw at creation time (and are compile errors first).

## Switching languages / reactivity

```typescript
i18n.setLanguage("tr");            // override (validate + notify listeners)
i18n.resetLanguage();              // clear override, re-run detection
i18n.currentLanguage;              // "tr"
i18n.currentLanguageMeta;          // { code: "tr", name: "Türkçe", intlLocale: "tr", dir: "ltr", ... }
i18n.currentDir;                   // "ltr" | "rtl" (defaults to "ltr")
i18n.currentIntlLocale;            // BCP-47 locale for Intl APIs (defaults to the code)
i18n.languageMetaList;             // ordered [{ code, name, ... }], ready for switcher menus
i18n.applyToDocument();            // sets <html lang> and <html dir> (no-op outside a browser)
const off = i18n.onLanguageChange((code) => { /* re-render */ });
```

Types derive from the instance, so no separate contract exports are needed:

```typescript
import type { LambderI18nCodes, LambderI18nKeys, LambderI18nTranslatorFor } from "lambder/client";

export type LanguageCode = LambderI18nCodes<typeof i18n>;       // "en" | "tr" | "ar"
export type I18nKey = LambderI18nKeys<typeof i18n>;             // "save" | "greet" | ...
export type I18nFunction = LambderI18nTranslatorFor<typeof i18n>;
```

Code that only reads translations (a component library, a formatter, a mail
renderer) can take any instance of one contract, whatever its language set,
as a `LambderI18nReadonlyInstance` of that contract. It holds what reading
takes (`t`, `forLanguage`, the `current*` members, `onLanguageChange`,
`isLanguageCode` and the registry), with language codes as plain strings, and
none of what changes an instance (`setLanguage`, `resetLanguage`,
`loadLanguage`, `registerDictionary`, `applyToDocument`, and
`checkPluralCoverage`, which loads every language) or builds one
(`extend`, `extendPartial`):

```typescript
import type { LambderI18nReadonlyInstance } from "lambder/client";
import { en } from "./en";                        // the default block, `as const`: the contract

export const greetingLine = (i18n: LambderI18nReadonlyInstance<typeof en>, name: string) =>
    `${i18n.t("greet", { name })} (${i18n.currentLanguage})`;

greetingLine(storefrontI18n, "Ada");              // an instance over en and es
greetingLine(warehouseI18n, "Ada");               // one over en, zh-Hant and ko
```

The module is framework-free; a Vue adapter is a few lines:

```typescript
import { shallowRef } from "vue";
import { i18n } from "@common/i18n";

export const t = shallowRef(i18n.t);
i18n.onLanguageChange(() => { t.value = ((...args) => i18n.t(...args)) as typeof i18n.t; });

// Apply the active language to the document (RTL support):
i18n.applyToDocument();
i18n.onLanguageChange(() => i18n.applyToDocument());
```

## Loading languages on demand

Every language written inline is bundled, and so downloaded by every visitor. To ship only the language a visitor reads, give a language a loader in place of its dictionary: a function that resolves to the dictionary, or to a module whose default export is the dictionary. The default language stays inline, because every lookup falls back to it and it is the typed contract.

```typescript
// en.ts: the default language, imported inline
export const en = { save: "Save", greet: "Hello {name}" } as const;
export type AppKey = keyof typeof en;
```

```typescript
// tr.ts: one language per file, the dictionary as its default export
import type { AppKey } from "./en";

export default {
    save: "Kaydet",
    greet: "Merhaba {name}",
} satisfies Record<AppKey, string>;
```

```typescript
import { en } from "./en";

export const i18n = createLambderI18n({
    languages: { en: { name: "English" }, tr: { name: "Türkçe" }, ar: { name: "العربية", dir: "rtl" } },
    defaultLanguage: "en",
    enforced: ["en"],
    base: {
        en,                                  // inline: the contract and the fallback
        tr: () => import("./tr"),            // loaded on demand
        ar: () => fetchDictionary("ar"),     // anything that resolves to a dictionary
    },
});

// The active language, before the first render. A failed load still renders,
// in the default language, rather than leaving a blank page.
await i18n.loadLanguage().catch((err) => console.error(err));
```

- A loader is checked against the same contract as an inline block: a loaded dictionary missing a key is a compile error that names the key. The `satisfies` line in the language file puts that error in the file itself.
- Inline blocks and loaders mix freely, per language. A config without loaders is unchanged, and `loadLanguage` has nothing to do for it.
- Keep the arrow: `import()` runs when it is evaluated, so `tr: import("./tr")` would fetch every language at startup. The path has to be a literal in your own code, where the bundler can see it and split the file out.
- Until a language has loaded, `t` falls back to the default language key by key, as it does for any missing translation, so await `loadLanguage` before the first render.
- `setLanguage(code)` switches at once and starts that language's loaders; change listeners fire for the switch and again when the dictionaries land. A failure there is logged, not thrown. To switch without a flash of the default language, load first, then switch:

```typescript
await i18n.loadLanguage("tr");
i18n.setLanguage("tr");
```

- `loadLanguage(code?)` defaults to the active language and loads that language for every instance sharing the root, whichever instance it is called on. Concurrent calls share each load, and change listeners fire once per load, when its dictionaries have been merged.
- A loader that answered never runs again. One that rejected (a network error, say) rejects `loadLanguage`, leaves the language falling back to the default, and runs again on the next call, so a retry is just another `loadLanguage`. One whose answer is refused (not a dictionary, redeclaring a parent key, or [changing a text's placeholders](#placeholders)) rejects once and its block is dropped.
- Creating an extension loads nothing. An extension created after its language was loaded (a component in a lazily loaded chunk) awaits its own `loadLanguage()`, which runs only what is still missing. Create extensions once, at module level, not per render.
- Translations passed to `registerDictionary` before a loader has run are kept over the ones it brings.

## Runtime dictionaries (fetched translations)

Dictionaries can be merged at runtime, e.g. locales fetched from an API instead of bundled. The compile-time contract still comes from the statically declared enforced blocks.

```typescript
const dict = await lambderCaller.public.getTranslations({ language: "tr" });
i18n.registerDictionary("tr", dict.translations);
```

Registrations on a parent are visible to all previously created extensions (lookup is layered, child-first), existing keys may be overridden, and change listeners fire, so reactive bridges re-render when translations arrive.

## Backend usage

The active-language state is process-global, so on the backend prefer the explicit form, because language is per-request. With loaders, load the language first; after the first request in a container it is already there. A failed load leaves `t` on the default language, which beats answering the request with an error:

```typescript
lambder.serveIndexHtml(async (ctx, res) => {
    const lang = pathLanguage(ctx.path);        // app logic
    await i18n.loadLanguage(lang).catch((err) => console.error(err));
    const t = i18n.forLanguage(lang);
    return res.templateFile("index.html", { title: t("mainTitle") });
});
```

## API reference

| Member | Description |
| --- | --- |
| `createLambderI18n(config)` | Create the root instance. Config: `languages`, `defaultLanguage`, `enforced`, `base` (any non-default language may be a loader), `detectLanguage?` |
| `t(key, params?)` | Translate in the auto-resolved language; a plural key's `params.count` picks the form |
| `forLanguage(code)` | Translator bound to an explicit language |
| `extend(dict)` | Strict extension: all languages required |
| `extendPartial(dict)` | Partial extension: only enforced languages required |
| `loadLanguage(code?)` | Run a language's loaders across the root (default: the active language); resolves once merged |
| `registerDictionary(code, dict)` | Merge translations at runtime, checked as inline blocks are (may override; notifies listeners) |
| `checkPluralCoverage()` | For a test or a build: load every language, then reject with every plural entry lacking a category its language uses |
| `setLanguage(code)` / `resetLanguage()` | Override / re-detect the active language, starting its loaders |
| `currentLanguage` / `currentLanguageMeta` | Active code / its metadata (with `code` injected) |
| `currentDir` / `currentIntlLocale` | Widened direction (default `"ltr"`) / Intl locale (default: the code) |
| `applyToDocument()` | Set `<html lang>`/`<html dir>` from the active language (browser only) |
| `onLanguageChange(cb)` | Subscribe to language/dictionary changes; returns unsubscribe |
| `isLanguageCode(v)` | Type guard for supported codes, spelled as registered |
| `languages` / `languageList` / `languageMetaList` / `defaultLanguage` / `enforced` | Registry introspection |

Exported types: `LambderLanguageMeta`, `LambderI18nConfig`, `LambderI18nInstance`, `LambderI18nReadonlyInstance<TContract>`, `LambderI18nTranslator`, `LambderI18nExtractParams`, `LambderI18nDictionaryLoader`, `LambderI18nDictionaryEntry` (a text or a plural entry), `LambderI18nPluralEntry`, `LambderI18nPluralCategory`, and instance-derived `LambderI18nCodes<T>` / `LambderI18nKeys<T>` / `LambderI18nTranslatorFor<T>`.
